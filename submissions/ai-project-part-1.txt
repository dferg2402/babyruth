# Issues found with AI generated requirements

There were many issues with the generated requirements given that the model used was SOTA (Claude Sonnet 4.6 Medium thinking):

Issue 1 - Hallucinated Requirement

Affected Requirement: REQ-11

What it says: When a user double-clicks an event card, the system shall immediately initiate the purchase of one ticket using the user's saved settings.

Why it's wrong: The transcript says the double-click should instantly buy one ticket, but nowhere does it define what "saved settings" are, or mention that users can save payment settings at all. The AI invented the concept of "saved settings". The transcript's version one has a simulated/pretend payment step with no real payment company involved, so there are no payment settings to save in the first place.

How to fix it: Remove "saved settings." The requirement should say the system initiates purchase of one ticket using the user's account and the system's default purchase flow (quantity = 1, user's previously selected or default currency).

Issue 2 - Hallucinated Requirement

Affected Requirement: REQ-12

What it says: While a user is not logged in and attempts to double-click an event card, the system shall prompt the user to log in before proceeding.

Why it's wrong: This was never discussed in the transcript. The meeting only established that checkout and order history require login (from Kenji). The double-click scenario was raised by Marcus as a UI convenience idea, and nobody discussed what happens if a non-logged-in user attempts it.

How to fix it: This is a legitimate missing exception that should exist, but it's technically hallucinated because it was never stated. It should be flagged as an inferred requirement, not a stated one, or converted to an open item pending team confirmation. Per Kenji's actual stated rule: checkout requires login, so this should be derived from REQ-15 rather than stated independently for double-click.

Issue 3 - Missing Requirement: Search by Date

Affected Requirement: No requirement covers this.

Why it's wrong: In the transcript, Marcus explicitly asks "Search by artist. What about by venue or date?", and while Darnell only confirmed venue, the date search was raised and never formally ruled out. Also, Adaeze's summary says "browse and search events by artist and venue", in which date was dropped without resolution. However, the event detail page (REQ-13) shows date/time, so filtering by date is a natural companion feature that was at minimum discussed.

How to fix it: Add a note that date-based search was raised but not confirmed. Either add it as an open item or add a requirement with an open-item tag.

Issue 4 - Missing Requirement: The Complete-Purchase-in-Under-Two-Minutes Goal

Affected Requirement: None.

Why it's wrong: Darnell explicitly stated: "I need one place where a student can see what's coming up, buy a ticket, and be done in under two minutes." This is a performance/UX requirement that the AI completely ignored. It's a non-functional requirement, but it was directly stated by the customer as a core goal.

How to fix it: Add a non-functional requirement stating the system shall enable a logged-in user to complete a ticket purchase within two minutes from the event browsing page.

Issue 5 - Missing Requirement: Screenshot Prevention on Confirmation Page

Affected Requirement: None.

Why it's wrong: Darnell explicitly requested: "make it so students can't screenshot the confirmation page." Marcus confirmed: "Noted. No-screenshot on the confirmation page." The AI dropped this entirely, even though it was explicitly agreed upon during the meeting.

How to fix it: Add a requirement that the confirmation page shall implement browser-level screenshot prevention.

Issue 6 - Missing Requirement: Specific Error Messages for Distinct Failure Types

Affected Requirement: REQ-20, REQ-21, REQ-23 partially cover this, but the broader requirement is missing.

Why it's wrong: Thuy specifically stated: "I want failures to be specific. 'Sold out' is a different message than 'invalid quantity' which is different from 'unsupported currency.'" The AI captured individual cases but never wrote a general requirement that each failure type must produce a distinct, named error message. REQ-20, REQ-21, and REQ-23 cover only three failure types. There is no requirement for what message appears when, for example, a user is not logged in and tries to check out.

How to fix it: Add a general requirement that for every failure condition in the purchase flow, the system shall display a distinct error message that identifies the specific cause of failure.

Issue 7 - Missing Requirement: Event Listing Must Show Upcoming Events (Not All Events)

Affected Requirement: REQ-07

What it says: "The system shall display a list of all upcoming events available on the platform."

Why it's wrong: This is actually correct, but there is no requirement about what happens to past events; Are they removed from the listing? Hidden? Archived? Darnell said students need to see "what's coming up", implying the browse view is future-facing. The AI never addressed what happens to past or sold-out events in the listing.

How to fix it: Add a requirement that past events (events whose date has passed) shall not appear in the main event listing. Separately, add a requirement about how sold-out events are displayed (shown with a "Sold Out" badge vs. hidden entirely - this may be an open item).

Issue 8 - Ambiguous Language in REQ-14

Affected Requirement: REQ-14

What it says: "When a user loads or refreshes an event detail page, the system shall display the current number of tickets remaining at the time of page load."

Why it's wrong: The word "current" is ambiguous. The transcript had a whole debate about this: Darnell said "live means live, when I look at my phone the number is right," but Thuy pointed out "the number can be right when the page loads and outdated four seconds later." Adaeze deferred this to be "spec'd precisely later." The AI resolved this ambiguity by choosing "at the time of page load", but that's an editorial decision the AI has no authority to make. This is an open item.

How to fix it: Reclassify as an open item. The requirement should be flagged as: "the ticket availability update mechanism (on-page-load only vs. real-time auto-updating) is an unresolved open item." It should not state a specific resolution.

Issue 9 - Ambiguous Language in REQ-22

Affected Requirement: REQ-22

What it says: "The system shall enforce a maximum ticket quantity per account per event of <limit TBD>."

Why it's wrong: The transcript shows a direct conflict between Marcus and Kenji on this point. Marcus said the cap is "a per-order thing, no single order above the limit." Kenji said "Per account, per event, that's what keeps a scalper from placing ten orders" and Marcus replied "Sure, sure." These are actually two different rules: a per-order cap AND a per-account-per-event cap. The AI collapsed them into one requirement and left the scope ambiguous.

How to fix it: Split into two requirements: (1) a per-order maximum quantity, and (2) a per-account-per-event cumulative maximum, both with TBD values.

Issue 10 - Incorrect Business Logic in REQ-24 / REQ-25

Affected Requirement: REQ-24, REQ-25

What REQ-24 says: "While a logged-in user's account is flagged as USF-eligible, the system shall apply the USF student discount to the ticket price at checkout."

Why it's wrong: REQ-25 correctly marks the scope of the discount as an open item, but REQ-24 implies the discount always applies, regardless of which events. The two requirements contradict each other: REQ-24 says the discount applies at checkout universally, while REQ-25 says the scope is unresolved. If the final decision is "USF-hosted events only," REQ-24 as written would be incorrect.

How to fix it: REQ-24 should be conditional on the resolution of REQ-25. It should read: "When a logged-in user's account is flagged as USF-eligible AND the event qualifies for the USF discount, the system shall apply the USF student discount."

Issue 11 - Missing Business Rule: Double-Click Requires Saved/Default Currency

Affected Requirement: REQ-11

Why it's wrong: The double-click feature is supposed to be frictionless or "one gesture and they're done." But the purchase flow (REQ-16) requires the user to select a currency. If double-click bypasses the purchase flow, what currency is used? The transcript never resolved this, and the AI didn't flag it as an open item. It just said "saved settings". This is a missing business rule.

How to fix it: Flag as an open item: what currency and quantity are assumed when a user double-clicks, given the purchase flow is bypassed?

Issue 12 - Duplicate / Redundant Requirements

Affected Requirements: REQ-02 and REQ-35

What they say:

REQ-02: "the system shall store the user's password as a cryptographic hash and shall never store the password in plaintext."
REQ-35: "The system shall never transmit or store user passwords in plaintext at any point in the application."

Why it's wrong: These two requirements cover the same rule. REQ-35 adds "transmit" which is a useful addition, but the "never store in plaintext" clause is stated twice. Redundant requirements create maintenance problems, if one is updated, the other may be missed, creating a conflict.

How to fix it: Merge into a single requirement: "The system shall hash all user passwords before storage and shall never store or transmit passwords in plaintext at any point."

Issue 13 - Missing Requirement: Order History Requires Authentication

Affected Requirement: REQ-36 covers this for checkout and order history access. However, REQ-30 states "While a user is authenticated, the system shall provide an order history page".

Actually missing: There is no requirement for what happens when an unauthenticated user directly navigates to the order history URL. REQ-36 says access is denied, but there's no requirement specifying the system must redirect them to login rather than showing an error page.

How to fix it: Add: "When an unauthenticated user attempts to access the order history page or checkout page, the system shall redirect the user to the login page."

Issue 14 - Non-Testable Requirement in REQ-39

Affected Requirement: REQ-39

What it says: "The system shall be accessible to any user worldwide without geographic restriction."

Why it's wrong: "Accessible to any user worldwide" is not testable as written. There's no measurable acceptance criterion. This came from Adaeze's framing statement: "EventHub is a public platform. Anyone in the world can register and buy tickets."

How to fix it: Rewrite as: "The system shall not implement any IP geolocation blocking, country-based access restrictions, or region locks on user registration or ticket purchasing."

Issue 15 - Missing Open Item: Rounding Rule Not Fully Specified in REQ-27

Affected Requirement: REQ-27

What it says: "...shall round the final converted price according to the rules of the target currency. (The precise rounding rule is an open item.)"

Why it's wrong: Kenji raised two separate sub-questions: (1) does the discount apply before or after currency conversion, and (2) where does rounding happen? REQ-27 answers question 1 correctly (discount before conversion), but that answer was never confirmed in the transcript. Marcus said "That's a good question" with no resolution. The AI chose an answer (discount first, then convert) without authority to do so.

How to fix it: The order of operations (discount then convert, vs. convert then discount) should also be flagged as an open item, not silently resolved.
